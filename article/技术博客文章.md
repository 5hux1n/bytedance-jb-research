# 拆解字节系 App 的越狱检测——一次 roothide 环境下的静态 + 动态联合逆向

> 本文是一次**合法安全研究**的记录。目标是把字节系 App 的越狱/注入检测与风控机制的"真实形态"搞清楚：它从哪些维度检测、检测逻辑如何实现、检测结果如何联动到上层。全程 Frida **只读**（只 `onEnter/onLeave` 读参数、读返回、backtrace、dump 内存，不修改任何返回值或字段），不包含任何绕过武器化内容。文中所有技术论断都以目标二进制中实际读出的指令、字符串、表结构与设备上的现场读数为依据；无法取得直接证据的判断，一律在文末如实标注为"不可验证"。
>
> 文中不提供任何 IPA、脱壳后的 Mach-O 或可直接运行的绕过代码。

---

## 0. 写在前面：为什么要联合逆向

纯静态分析能看到"代码里写了什么检测"，但看不到"哪条真的在跑"；纯动态能看到"跑了什么"，但看不到被混淆、被延迟触发、或当前环境没走到的分支。字节系 App 恰好把两者的盲区都占满了：

- 单个主二进制 500 MB 级别、ObjC 类数以万计；
- 关键符号在**运行期**才用 `dlsym` 解析，只看导入表会系统性低估检测面；
- 字符串两套变体加密，方法 IMP 走三跳分支岛，子系统入口全部运行期分发。

所以本文采用静态（Capstone + 自写 ObjC/交叉引用索引 + 离线批量解密）与动态（Frida 只读观测）互为印证的方式，最后再用 IDA Pro 9.3 的 Hex-Rays 对关键函数做第三方交叉验证。

### 分析对象与环境

| 项 | 值 |
|---|---|
| 番茄小说 | 7.4.1（`com.dragon.read` / 主二进制 `Reading`） |
| 红果短剧 | 7.4.1（`com.phoenix.video` / 主二进制 `Eggplant`） |
| 抖音 | 40.8.0（`com.ss.iphone.ugc.Aweme` / 主二进制 `AwemeCore`） |
| 设备 | iPhone 11 Pro Max（`iPhone12,5`），iOS 26.0，roothide（relaxin） |
| Frida | host 17.7.3 ↔ device 17.23.3 |

一个动态侧必须交代的坑：host 与 device 版本错位导致 `Module.getExportByName` / `Process.findExportByName` 已被移除，必须改用 `Module.getGlobalExportByName`；attach 还有严格时序——`spawn → resume → 等 2~4 s → attach`，早于 ~0.9 s attach 进程约 1 s 被杀，而在 hook 回调里直接调 ObjC 会重入死锁拖垮整机（实测掉过一次线）。这些约束决定了"启动头两秒窗口"天然测不到，后文会再提。

分析期间自然产生了一个对照组：会话中途设备崩溃恢复，jbroot 哈希从 `.jbroot-4C4DC0C67115CBA8` 变成 `.jbroot-8FF0E778ECD87DA9`，注入层结构一致，正好用来验证结论的稳定性。

## 1. 第一个发现：三款 App 共用同一套安全组件

同一把 XOR key 下，相同明文对应的密文完全相同，因此可以直接拿**密文**做跨 App 指纹。这把钥匙后面会详细讲，先看结论。

### 1.1 运行期符号名表：番茄 ≡ 红果，逐字节同一

把加密池里的一组密文解出来，是这样 15 条：

```
dladdr  stat  lstat  fopen  __opendir2  getifaddrs
CCCryptorCreateWithMode  CCCryptorUpdate
CFNetworkCopySystemProxySettings  CFBundleIdentifier
Filter  .plist  libdyld.dylib  libcommonCrypto.dylib  CFNetwork
```

番茄这 15 条落在 `0x112F3C29A` 起的一段，红果落在 `0x11335A19A` 起的一段，**偏移恒定 `0x41DF00`，15/15 一一对应，连"哪条用加密变体 v1、哪条用 v2"都完全相同**。

这里有个容易被原始分析带偏的点：这**不是**越狱路径黑名单，而是 **`dlsym` / CFNetwork 的运行期符号名表**。App 在运行期用 `dladdr`/`dlsym` 去解析 `stat / lstat / fopen / __opendir2 / getifaddrs` 这些 libc 符号——这正是"只读导入表会低估检测面"的直接证据：这些函数在导入表里根本不出现。

抖音是同一框架的**不同配置子集**：`CCCryptorCreateWithMode`、`CFNetworkCopySystemProxySettings`、`CFBundleIdentifier`、`libcommonCrypto.dylib` 在；部分密文缺失；池内额外多出 `com.bytedance.safeguard.data`——第一次出现"safeguard"这个自曝家门的字符串。

### 1.2 规则引擎：同一台 VM，只是配置规模不同

三款都带一台"字段求值虚拟机"，原语逐字节同构，差别只在喂进去的规则数：

| App | 规则条目 | 键名范围 | 注册函数 | VM 读 / 写原语 |
|---|---|---|---|---|
| 番茄 | 15 | `G0` + `CF0..CFD` | `0x10185ADF8` | `0x1019A08E4` / `0x1019A08F0`（`ctx+0x6070+idx*8`） |
| 红果 | 15 | `G0` + `CF0..CFD` | `0x1017DBDD0` | 同构 |
| 抖音 | 66 | `G0..G7` + `CF0..CF39` | `0x77AB3B4` | `0x78BDAB8` / `0x78BDAC4`（同构） |

读写原语都是 `ctx + 0x6070 + idx*8` 这种裸的槽位存取，三款逐字节一致。到这里"字节内部公共安全组件"已经不是推测，而是逐字节级的事实——**但要强调：横向比对在本研究里只是辅助印证手段，主线是把机制本身讲清楚。** 下面开始拆机制。

## 2. 检测链的真实形态：它挂在 HMD 上报链上

原始分析最大的空白是"检测到底在什么时候、被谁调起"。动态 backtrace（Frida 权威符号化，非推测）把这条链钉死了：

```
+[SSLaunchMonitor markFirstClassLoad]
 ├─ +[HMDTTMonitorHelper reportHeaderParamsWithInjectedInfo:]   （性能上报）
 ├─ -[HMDExceptionModuleReporter _reportExceptionData]          （异常上报）
 └─ +[HMDConfigHelper requestHeaderFromProvider:]               （远程配置拉取）
      └─ -[HMDUploadHelper headerInfo]        0x10A09EDBC
           └─ -[HMDInfo isEnvAbnormal]        0x10A09F728
                └─ dispatch_once
                     └─ 0x10A09F79C   statfs × 93 路径 + /hmd_tmp_file 越界写
```

HMD 是字节的 Heimdallr 监控框架。关键认知有两点：

1. **触发时机不是"启动检测一次"，而是每次构造 HMD 上报 header**——性能、异常、远程配置三条并列路径都会走到，沙盒探测结果用 `dispatch_once` 缓存一次。
2. **真正的检测体 `0x10A09F79C` 干两件事**：对 93 条路径跑 `statfs`，以及往 `/hmd_tmp_file` 做一次沙盒越界写。

越狱标志最终进了哪里？进了 HMD 上报 header 的**明文字典**（34 个字段），其中有一个字段叫 `is_env_abnormal`。这一点很重要——它否定了"越狱标志走 protobuf、字段名不可见"的旧假设：至少 HMD 这条通道是明文可读的。

## 3. 那些"看起来在检测"、其实没在跑的代码

逆向最容易犯的错，是把二进制里存在的检测代码直接当成"正在生效的检测"。这次最有价值的几个结论恰恰相反。

### 3.1 `fopen` 五探针 = 死代码（三重独立证据）

有一族 `fopen` × 5 路径的探针（`0x10250F8C4`，同族还有个开关不同的 `0x10264A018`），形态非常像经典越狱文件检测。但三条独立证据一致判它死亡：

| 证据 | 方法 | 结果 |
|---|---|---|
| 静态引用 | `ADRP+ADD/LDR`、chained 指针槽、相对指针、`__init_offsets`、base 相对表 全扫 | 全 0 |
| 运行期登记 | 模块非可执行段 23,674,880 B 全扫函数指针 | 0 命中 |
| 运行期调用 | 45 s 会话计数 | 0 次 |

静态零引用、内存零登记、运行时零调用——这不是"没触发"，是根本没有可达入口。真正跑在链上的是上一节那个 `statfs` 版本。

### 3.2 `statfs` 的 93 条路径，在 roothide 上全部 miss

`statfs` 这条是真的在跑（挂在 HMD 链上），但它查的是什么、查中没有，是两回事。先做一件原始分析没做到的事：**把三款里每一处 `statfs` 族调用全部静态定性**。

`statfs` 普遍走 `分支岛 → 二级片段 → stub` 三跳，只扫 `BL` 到 stub 会漏掉大部分调用点。按三跳展开后，番茄与红果各 **12** 处 `statfs` + 3 处 `statvfs` + 2 处 `fstatfs`（又一处数字完全相同的同组件证据）。逐处看它们读没读 `f_flags`（偏移 0x40）、`f_type`（偏移 0x3c）：

- `f_flags` 读取次数 = **0 / 17**。

这意味着**全部 17 处没有任何一处做 `f_flags & MNT_RDONLY` 的"根分区被重挂载为可读写"判定**。原始分析里"statfs 可能用于根分区 remount 检测"的猜测，由此从"动态单点否证"升级为"全调用点静态穷举否证"。`statfs` 族的真实用途只有三类：路径存在性探测（93 项表，用 `tbnz`/`cmn w0,#1` 把返回码布尔化）、磁盘空间查询、以及唯一一处 `f_type` 文件系统类型判定（`0x101866E70`）。

动态侧补刀：93 路径（去重 50 条）在本机实测 **434 次探测 / 0 命中**。这些是 Cydia 时代的 `/private/var/...` 老路径，在 roothide 的 rootless 布局下自然一条都对不上。

### 3.3 SafeGuard 规则引擎：一台没通电的状态机

前面那台 VM（`CF0..CFD`）看着像"逐项越狱检查清单"，实际逆出来是一套**通用字段求值 VM**：`field[6]` 是结果位，`field[8..12]` 是输入槽，每条规则读 N 个输入、调一个专属 helper、写 `field[6]`。helper 本身是通用运行时函数（lazy-init、`[x0+0x110]` 取对象、分支岛），不是"检查某个越狱特征"的领域谓词。

更关键的是可达性。对规则注册函数做穷尽排查：

| 来源 | 结果 |
|---|---|
| `BL/B`（三个可执行节） | 0 |
| `ADRP+ADD/LDR`（寄存器生命周期感知） | 0 |
| chained 指针槽 / int32 / int64 相对指针（全部节） | 0 |
| `__init_offsets` 静态构造表（2903 项） | 不在表内 |
| 运行期 VM 原语调用计数（番茄 / 抖音） | 0 / 0 |

**六路引用全 0，不在静态构造表，运行期零调用**——这台 VM 在当前构建里没有静态可达入口，运行期也从没被调起。旁证：它的沙盒目录 `.../Library/Heimdallr/CrashCapture/LoadLaunch/SafeGuard` 确实存在（模块初始化过），但规则求值没有发生。换句话说：引擎装好了、通电了，但没人踩油门。

## 4. roothide 下到底命中了什么

把所有探针在本机的真实表现列成一张表（两次 jbroot 哈希都测过）：

| # | 探针 | 实现位置 | 本机实测 | 判定 |
|---|---|---|---|---|
| 1 | `fopen` × 5 路径 | `0x10250F8C4` / `0x10264A018` | 零引用/零登记/零调用 | 死代码 |
| 2 | dyld 镜像名 5 子串 | `0x1083E1854` | 1118 次调用 / **1 次命中** | 靠目录名巧合命中 |
| 3 | `statfs` × 93 路径 | `0x10A09F79C` | 434 次探测 / 0 命中 | 全 miss |
| 4 | `/hmd_tmp_file` 越界写 | `0x10A09F79C` 内 | fd = -1 → `is_env_abnormal=1` | 触发（极性见下） |
| 5 | 逐镜像 `isEnvAbnormal` | `HMDCrashBinaryImage` | 读 1117 次，全 0 | 未标记任何注入库 |
| 6 | 规则引擎 `G0/CF0..CFD` | `0x10185ADF8` | 0 次调用 | 未参与判定 |
| 7 | `canOpenCydia` | `0x1074B70B8` | 未触发；且 `cydia` 未在 `LSApplicationQueriesSchemes` 声明 → iOS 15+ 恒假 | 逻辑上无效 |
| 8 | `canGetAllAppName` | `0x1074B7138` | 未触发 | 未测 |

### 4.1 最有意思的一条：唯一的"命中"是目录名撞名

探针 2 遍历已加载镜像名，拿去比对 5 条子串。roothide 全套注入库的名字**一条都不匹配**：

```
/usr/lib/systemhook-8FF0E778ECD87DA9.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothideinit.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothidepatch.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/libroothide.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/ellekit/libinjector.dylib
```

唯一命中的是：

```
.../.jbroot-8FF0E778ECD87DA9/usr/lib/TweakInject/FakeTweak.dylib
```

命中原因是路径里含 **`TweakInject`**（名单第 3 条），属于**目录名撞名**，不是库名命中。所以"旧名单对 rootless/roothide 没跟进"这个说法要精确修正为：**旧名单在 roothide 上由一次目录名巧合命中，5 个核心组件里 4 个被漏检。**

### 4.2 越界写的极性：普通设备可能也报 1

探针 4 是本地唯一真正给出非零结论的检测。静态看：`0x10A09F800` 处 `open_dprotected_np("/hmd_tmp_file", O_CREAT|O_RDWR)`，随后 `tbnz w0,#0x1f` 判符号位——**失败置 1、成功置 0**。动态看：本机 fd = -1（失败）→ 缓存 1 → `-[HMDInfo isEnvAbnormal]` 返回 1 → header 里 `is_env_abnormal = "1"`。

但这里有个诚实必须交代的疑点：按这条指令，"写失败 → 异常"意味着**普通未越狱设备在同一沙盒位置写失败时同样会报 1**。所以 `is_env_abnormal` 这个字段的真实语义，必然要结合服务端判定，本地只能还原到"写失败→1"这一步。本文不对后端含义做推断。

## 5. 解密体系：把整个加密字符串池逆出来

前面所有"解出某某字符串"都依赖同一把钥匙。完整逆出来是这样。

### 5.1 算法（key = `0xDEADBEEF`）

```
变体 1（0x109F8B83C）：
  整词: plain_word[i] = ror32(cipher_word[i] ^ 0xDEADBEEF, 23)      ; 4 字节小端
  尾部: plain_byte[j] = cipher_byte[j] ^ ((0xDEADBEEF >> (8*(j%4))) & 0xFF)

变体 2（0x109F778F4）：
  整词: plain_word[i] = cipher_word[i] ^ cipher_word[i-1] ^ 0xDEADBEEF
  尾部: 同变体 1
```

关键点在尾部：不满 4 字节的尾巴不走整词路径，而是逐字节异或 key 的低位字节。漏掉这一段，就会出现"最后 1~3 字节乱码"——这是早期分析踩过的坑，也是判断算法是否真正逆对的试金石。

实现上还有个陷阱：两个真身各挂一个分支岛（`0x107C16440` / `0x107C16448`），**hook 必须挂真身**，挂在岛上 `onLeave` 读到的是还没写入的缓冲。静态上 15 个调用点全部集中在 `0x1019616xx–0x1019624xx` 一个函数簇里。

### 5.2 全池批解：`__const` 7.89 MB → 11,812 条明文

两变体 × 两种对齐批量解密、去重后得到 **11,812 条不同明文**（路径 189、bundle-id 16、纯标识符 1,026、其他 10,581）。越狱/注入相关命中 19 条，其中 6 条是原始 50 条路径名单里完全没有的：

```
com.opa334.Dopamine            com.opa334.Dopamine.roothide
com.roothide.manager           com.roothide.manager.plist
com.xina.jailbreak.plist       com.xina.blacklist.plist
```

这改写了"名单只覆盖 Cydia 时代"的旧印象：**名单其实覆盖了 Dopamine（rootless）/ roothide / Xina 三代，但用的是 bundle-id 与 plist 名，不是路径与库名。** 这正是此前只做路径扫描完全看不到它们的原因。原 50 条路径里有 29 条能在加密池对上，仍然缺席的是 `ellekit`、`libhooker`、`/var/jb`、`substitute`、`trollstore`。

### 5.3 roothide 密文块是惰性的

池里确实存在 `com.roothide.manager`、`com.opa334.Dopamine.roothide`、`Documents/bootstrap.tar`、`/var/mobile/Library/HTTPStorages` 这些 roothide 特征串，且可解。但三条独立证据表明当前环境没有任何路径会去解它们：静态五种编码 × 三个可执行节 + 数据段指针引用全 0；778 MB 可写区间扫三条明文 0 命中；hook 两个解密真身 22 s，13 次调用全部落在符号名表 `0x112F3Cxxx`，无一进入密文块所在的 `0x112F15Cxx`。

密文在、能解、但在 roothide + 正常使用 + 无崩溃上报的条件下不可达。

## 6. 控制流平坦化：点状，而非整库

很多人默认大厂 App 是整库 OLLVM。实测不是。判据：`br xN` 前 7 条指令内同时出现 `adr` + `ldrsw/ldrb` + `add`，站点间距 ≤2KB 聚为一函数。

| 二进制 | dispatch 站点 | 聚类 ≈ 函数 | 覆盖代码 | 占 `__text` |
|---|---|---|---|---|
| 番茄 Reading | 10,589 | ≈4,925 | ≈2,582 KB | **0.89%** |
| 抖音 AwemeCore | 25,155 | ≈11,280 | ≈5,341 KB | **0.81%** |

**只有 0.8–0.9% 的代码被平坦化，点状分布在安全/风控相关模块**——这也是为什么大部分代码能直接读。

这里补一个抖音侧的分析缺陷修正，影响上面的计数口径：原始的函数起点识别只认三类序言（`sub sp` / `stp` 预索引 / `pacibsp`），必然漏掉无栈帧的叶子函数（典型如 `0x1E6EF964` 那种 `adrp/ldrsw/ldr/ret` 的 getter）。以 ObjC IMP 为真值实测，CJPay 窗口覆盖率只有 **16.9%**；叠加"终结指令（`ret`/`b`/`br`/`udf`）之后线性扫描起点"的补全后拉到 **97.2%**。因此此前对抖音任何"函数级"的统计都系统性低估了叶子函数占比，校正后抖音侧函数边界与番茄同样可信。

## 7. 用 IDA Hex-Rays 做第三方交叉验证

前面的结论来自自写工具链（Capstone + numpy 交叉引用索引）。为避免"自己验自己"，最后用 IDA Pro 9.3 的 Hex-Rays 独立复核。

直接 `idat -A` 导入 508 MB 的 `Reading` 在 16 GB 机器上不可行（卡在 ObjC 解析 >750 s，`.id0` 2.1 GB；`idalib` 无分析加载也 >600 s 未返回）。改走**雕刻子二进制**：按目标函数取 ±1~4 KB 窗口包成最小 ELF64（`PT_LOAD.p_vaddr` 保持原始虚拟地址），用 `idalib.open_database(run_auto_analysis=False)` + `add_func` + `ida_hexrays.decompile`，每函数约 1 秒。跨切片调用显示为 `MEMORY[addr]()`、尾调用显示为 `JUMPOUT(addr)`，地址与原二进制一致。

11 个关键函数全部与手工结论逐条对上，摘几条：

| 目标 | Hex-Rays 反编译要点 | 与手工结论 |
|---|---|---|
| `dec_v1` `0x109F8B83C` | `HIDWORD(v6)=c^0xDEADBEEF; out=v6>>23`；尾部 `out=c^(0xDEADBEEF>>v7)` | 一致（整词 ROR23 + 尾部逐字节） |
| `sandbox_statfs93` `0x10A09F79C` | `while(v0!=344)`→43 项，`while(v0!=400)`→50 项；`open(...,514)`；`if (fd & 0x80000000) →1 else {close;unlink;→0}` | 一致（43+50 / `/hmd_tmp_file` / `O_RDWR\|O_CREAT=0x202` / fd 符号位） |
| `vm_get/vm_set` | `*(qword*)(a1 + 8*a2 + 24688)` | `24688 = 0x6070`，一致 |
| `pred_inject_substr` `0x1083E1854` | `if (v2==40)` 循环比对 | `40/8 = 5` 项，一致 |
| `sysctl_caller` | `mib[2]=1; mib[3]=pid`；返回后浮点换算，**全程无 `0x800` 测试** | 一致（无 P_TRACED 判定） |

这些数都能自洽验算：`344/8=43`、`400/8=50`、`40/8=5`、`514=0x202=O_RDWR|O_CREAT`、`24688=0x6070`，`0xDEADBEEF` 低字节 `EF BE AD DE`，且 `(((x<<32)|x)>>23)` 的低 32 位恰好等于 `ror32(x,23)`。手工逆向与 Hex-Rays 无一处需要推翻的差异。

## 8. 对一些常见假设的修正

这次推翻/收紧了若干看似"显然"的结论，列出来比结论本身更有价值：

1. **`fopen` 五探针不是主检测，是死代码**（静态零引用 + 内存零登记 + 运行时零调用）。
2. **`statfs` 不做 remount 判定**：全 17 处调用点 `f_flags` 读取 0 次，猜测被全调用点穷举否证。
3. **"反调试走 sysctl 查 P_TRACED"不成立**：mib 常量静态验证确为 `{1,14}`、`size=648`（`kinfo_proc`），形态像经典探针；但全 `__text` 无 `AND #0x800`，4 个 `_sysctl` 调用点附近无 bit11 测试，返回后是对结构头做浮点换算——sysctl 只用于取进程信息，没有实现 P_TRACED 判定。
4. **加密池不是越狱路径表，是 dlsym/CFNetwork 符号名表**（15 条）。
5. **名单覆盖三代越狱**（Dopamine/roothide/Xina），但以 bundle-id 和 plist 名出现，不是路径。
6. **越狱标志 HMD 通道是明文字典**（34 字段，含 `is_env_abnormal`），不是不可见的 protobuf。
7. **平坦化仅 0.8–0.9%**，点状分布于安全模块，非整库 OLLVM。
8. **规则引擎在本构建不可达**：六路引用全 0、运行期零调用，但模块初始化确实发生过。

## 9. 没能验证 / 无法验证的

诚实地列出边界：

- **启动 0–2 s 窗口内规则引擎是否跑过一次**：更早 attach 会打死进程，这个窗口测不到。
- **崩溃上报路径是否会解密 roothide 密文串**：唯一验证方式是人为制造崩溃，那会改变目标行为，属于自设红线，不做。
- **`is_env_abnormal` 的后端语义**：需服务端对照，本地只能还原到"写失败→1"。
- **SafeGuard 调用方是否在 Swift 侧**：Swift 字面量走 `__swift5_reflstr` 相对偏移表，ARM64 引用扫描覆盖不到。
- **CJPay `appendParamTo:` 的真实 key**：番茄/抖音充值均为 App Store 内购，无第三方支付入口，这条链从未执行，客观拿不到。

## 10. 结论与思考

把机制收束成几句话：

1. **三款 App 共用一套安全组件**：符号名表 15/15 逐字节同一（偏移恒定 `0x41DF00`），规则引擎 VM 原语逐字节同构，差别只在规则配置规模（番茄/红果 15 条、抖音 66 条）。

2. **真实检测面比"代码里写了多少检测"窄得多**：`fopen` 五探针是死代码；`statfs` 93 路径在 roothide 上全 miss；`canOpenCydia` 因未声明 scheme 恒假；文件遍历链需要支付页才跑而本机无此入口。本地唯一真正给出非零结论的，只有 `/hmd_tmp_file` 越界写（→ `is_env_abnormal=1`）和那次目录名巧合命中。

3. **最该当成结论的，不是"某个探针是否命中"，而是这套防静态分析的设计是系统性的**：运行期符号名解析、方法 IMP 三跳分支岛、字符串两套变体加密、子系统入口全部运行期分发——四者叠加，使"只读导入表 + 只看调用图"的分析必然遗漏检测面。单看任何一层都会得出偏乐观的结论。

4. **对抗的真正边界在服务端**：本地最强的一条（越界写）也只产生一个语义存疑的上报字段，识别与否最终由服务端结合设备指纹决定。纯静态/本地动态能还原到"采集什么、怎么上报"，但服务端如何裁决属于不可见区。

对做越狱检测的人，反过来读也成立：把检测逻辑藏进运行期解析和点状平坦化、把判定搬到服务端，确实显著抬高了纯静态分析的成本——但一旦允许只读动态观测，"哪条真在跑"仍然会暴露无遗。攻防的价值，恰恰在于把"看起来在检测"和"真的在检测"区分开。
