## 三、核心结论二：检测链的真实形态

### 3.1 原报告的最大空白已补上：检测挂在 HMD 上报链上

backtrace（Frida 权威符号化，非推测）：

```
+[SSLaunchMonitor markFirstClassLoad]
 ├─ +[HMDTTMonitorHelper reportHeaderParamsWithInjectedInfo:]      （性能上报）
 ├─ -[HMDExceptionModuleReporter _reportExceptionData]             （异常上报）
 └─ +[HMDConfigHelper requestHeaderFromProvider:]                  （远程配置拉取）
      └─ -[HMDUploadHelper headerInfo]          0x10A09EDBC
           └─ -[HMDInfo isEnvAbnormal]          0x10A09F728
                └─ 0x10A09F744 → 0x10A09F764（dispatch_once）
                     └─ 0x10A09F79C  statfs × 93 路径 + /hmd_tmp_file 越界写
```

**触发时机**：不是"启动一次"，而是**每次构造 HMD 上报 header**（三条并列路径），沙盒结果用 `dispatch_once` 缓存。

### 3.2 `fopen` 五探针 = 死代码（三重独立证据）

| 证据 | 结果 |
|---|---|
| 静态引用（`ADRP+ADD/LDR`、chained 指针槽、相对指针、`__init_offsets`、base 相对表） | 全 0 |
| 运行期内存登记（模块非可执行段 23,674,880 B 全扫指针） | 0 命中 |
| 运行期调用（45 s 会话） | **0 次** |

同一族还有第二个实现 `0x10264A018`（开关全局不同），同样零引用。**真正跑在链上的是 statfs 版。**

### 3.3 文件探测的三条实现

| 实现 | 位置 | 判据 | 实际状态 |
|---|---|---|---|
| `fopen` × 5 | 0x10250F8C4 / 0x10264A018 | `FILE*` 非空 | **死代码** |
| `statfs` × 93 | 0x10A09F79C | `statfs()` 返回 | HMD 链，**已运行** |
| `-[NSFileManager fileExistsAtPath:]` × N | 0x1074B7034（`hasJailBreakFiles`） | BOOL | CJPay 链，**无第三方支付入口，未触发** |

### 4.1 第 2 项的细节（最有价值的实测）

被检查的镜像名里，roothide 全套库**一条都不匹配 5 条子串**：

```
/usr/lib/systemhook-8FF0E778ECD87DA9.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothideinit.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothidepatch.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/libroothide.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/ellekit/libinjector.dylib
```

命中的唯一一条是：

```
.../.jbroot-8FF0E778ECD87DA9/usr/lib/TweakInject/FakeTweak.dylib
```

原因：路径含 **`TweakInject`**（名单第 3 条），属于**目录名撞名**，不是库名命中。

**结论修正如上**：原报告"对 rootless/roothide 没有跟进"应改为——**旧名单在 roothide 上由"目录名巧合"命中一次**，4/5 的 roothide 组件被漏检。

### 4.2 第 4 项的极性

- 静态：`0x10A09F800 open_dprotected_np("/hmd_tmp_file", O_CREAT|O_RDWR)` → `tbnz w0,#0x1f` → **失败置 1、成功置 0**
- 动态：实测 fd = -1（失败）→ 缓存 1 → `-[HMDInfo isEnvAbnormal]` 返回 1 → header 中 **`is_env_abnormal = "1"`**（首次 header 早于 `dispatch_once` 完成时为 `"0"`）
- **未解释**：按该指令，"写失败 → 异常"意味着普通未越狱设备同样报 1。字段语义需后端对照，本文只陈述实测与指令，不推断后端含义。

### 5.1 语义（字段级，已还原）

| 来源 | 结果 |

**结论**：规则注册函数在本构建中**不存在静态可达入口，运行期也未被调用**。规则引擎处于未激活状态。

## 六、解密体系（完整逆出）

### 6.1 算法

```
变体 1（0x109F8B83C）：
  整词: plain_word[i] = ror32(cipher_word[i] ^ 0xDEADBEEF, 23)     ; 4 字节小端
  尾部: plain_byte[j] = cipher_byte[j] ^ ((0xDEADBEEF >> (8*(j%4))) & 0xFF)   ; 1~3 字节

变体 2（0x109F778F4）：
  整词: plain_word[i] = cipher_word[i] ^ cipher_word[i-1] ^ 0xDEADBEEF
  尾部: 同变体 1
```

**关键点**：尾部不走整词路径，而是逐字节异或 key 的低位字节。漏掉这一段就会出现"最后 1~3 字节乱码"（本项目早期现象）。


### 6.2 调用布局

- 两个真身各对应一个分支岛（`0x107C16440` / `0x107C16448`）。**hook 必须挂真身**，挂岛上 `onLeave` 读到的是尚未写入的缓冲。
- 静态共 15 个调用点，全部集中在 `0x1019616xx–0x1019624xx` 一个函数簇内。

---

### 6.3 全池批解结果（`__const` 7.89 MB）

两变体 × 两种对齐（0 / +2 位移）批量解密、去重后：**11,812 条不同明文**（路径 189、bundle-id 16、纯标识符 1,026、其他 10,581）。

越狱/注入相关命中 19 条，其中 **6 条是原报告 50 条路径里没有的**：

```
com.opa334.Dopamine            com.opa334.Dopamine.roothide
com.roothide.manager           com.roothide.manager.plist
com.xina.jailbreak.plist       com.xina.blacklist.plist
```

原报告 50 条路径中，加密池里能对上 **29/50**（其余只存在于明文 93 项表里）。仍然**没有**出现的：`ellekit`、`libhooker`、`/var/jb`、`substitute`、`trollstore`。

→ **名单已覆盖 Dopamine（rootless）/ roothide / Xina 三代，但用的是 bundle-id 与 plist 名，不是路径与库名。** 这正是此前只做路径扫描看不到的原因。

### 6.4 平坦化地图（目标 E）

判据：`br xN` 前 7 条指令内同时出现 `adr` + `ldrsw/ldrb` + `add`；站点间距 ≤2KB 聚为一函数。

| 二进制 | dispatch 站点 | 聚类≈函数 | 覆盖代码 | 占 `__text` |
|---|---|---|---|---|
| 番茄 Reading | 10,589 | ≈4,925 | ≈2,582 KB | **0.89%** |
| 抖音 AwemeCore | 25,155 | ≈11,280 | ≈5,341 KB | **0.81%** |

最密集段（番茄）：`0x105B00000`、`0x103000000`、`0x101C00000`、`0x102700000`、`0x111300000`。

结论：**点状布置在安全/风控相关模块，不是整库混淆**——所以大部分代码仍可直接读。



### 6.5 Hex-Rays 交叉验证（IDA Pro 9.3 + 雕刻子二进制）

`Reading` 单文件 508 MB、ObjC 类 78,911 个，`idat -A` 全量导入在 16 GB 机器上不可行（卡在 ObjC 解析 >750 s，`.id0` 2.1 GB）。改用**雕刻子二进制**：按目标 ±1~4 KB 取窗口包成最小 ELF64（`p_vaddr` 保持原虚拟地址），`idalib.open_database(run_auto_analysis=False)` + `add_func` + `ida_hexrays.decompile`，每函数约 1 秒。产物：`analysis/fanqie/hexrays_f5.md`（1,242 行 / 11 个函数）。

| 目标 | 反编译要点 | 与手工结论 |
|---|---|---|
| `dec_v1` | `HIDWORD(v6)=cipher^0xDEADBEEF; out=v6>>23;` 尾部 `out_byte=c^(0xDEADBEEF>>v7)` | 一致（整词 ROR23 + 尾部逐字节） |
| `sandbox_statfs93` | `while(v0!=344)`→43 项；`while(v0!=400)`→50 项；`open(0x1136AD0D6, 514)`；`if (fd & 0x80000000) → 1 else {close;unlink;→0}` | 一致（43+50 / `/hmd_tmp_file` / 0x202 / fd 符号位） |
| `vm_get` | `*(qword*)(a1 + 8*a2 + 24688)` | 24688 = 0x6070，一致 |
| `pred_inject_substr` | `if (v2==40)` 循环比对 5 项 | 一致 |
| `sysctl_caller` | `mib={const(1,14), 1, pid}`，之后 `v5=0; if(!ret){浮点}` | 一致，且**无 0x800 测试** |

→ 手工逆出的算法与 Hex-Rays 输出逐条对得上，无需推翻的差异。局限：切片外调用显示为 `MEMORY[addr]()`，只适合验证已定位函数。

## 八、未验证 / 不可验证项（如实列出）

| 项 | 原因 |
|---|---|

## 九、研究结论

1. **三款 App 共用一套组件**：符号名表 15/15 逐字节同一（偏移恒定 `0x41DF00`），规则引擎 VM 原语逐字节同构，差别只在**规则配置规模**（番茄/红果 15 条，抖音 66 条）。

2. **真实检测面比原报告描述窄得多**：`fopen` 五探针是死代码；`statfs` 93 路径在本机全 miss；`canOpenCydia` 因未声明 scheme 而恒假；`fileExistsAtPath` 链需要支付页才跑（而本机无该入口）。**唯一真正跑起来并给出非零结论的只有 `/hmd_tmp_file` 越界写（→ `is_env_abnormal=1`）与"目录名巧合命中"。**

3. **规则引擎（SafeGuard）在本构建中不可达**：六路引用全 0、不在静态构造表、运行期零调用，但模块初始化确实发生过（沙盒目录存在）。它的规则数据里含 roothide 特征串，却没有任何可达路径会解密它们。

4. **防静态分析的设计是系统性的**：运行期符号名解析（dlsym 名表加密）、方法 IMP 走三跳分支岛、字符串两套变体加密、子系统入口全部运行期分发——三者叠加，使"只读导入表 + 只看调用图"的分析必然遗漏检测面。这一点比"某个探针是否命中"更值得作为结论。

5. **对抗的边界在服务端**：本地最强的一条（越界写）只产生一个上报字段，且语义存疑；识别与否最终由服务端结合设备指纹决定。
