## 第二部分：静态分析实操流程（IDA / Ghidra）

### 阶段 0 — 解包与侦察
1. `unzip xxx.ipa`，进入 `Payload/xxx.app/`
2. 读 `Info.plist`：重点看 `LSApplicationQueriesSchemes`（往往直接暴露要探测的 scheme，如 cydia/sileo）、`CFBundleShortVersionString`（记录版本）
3. `otool -L 主二进制`：看链接了哪些库，是否有可疑的安全/风控相关 framework
4. `otool -l 主二进制 | grep -A4 LC_ENCRYPTION_INFO`：看 `cryptid`
   - `cryptid = 0` → 未加密，可直接分析
   - `cryptid = 1` → FairPlay 加密，需先获得脱壳后的 Mach-O 再做静态分析
5. 字节系 App 多为超大体积、含大量自研组件，注意识别 App 内嵌的 `.framework`（在 `xxx.app/Frameworks/` 下），**安全/风控逻辑很可能封装在独立 framework 内**，优先定位这些组件。

### 阶段 1 — 加载与预处理
- IDA：加载主二进制及各 Frameworks，等待自动分析完成；启用 Objective-C 解析，确保 selector/class 还原
- Ghidra：新建 project，导入所有 Mach-O，运行 auto-analysis（勾选 Objective-C / Swift 相关分析器）
- 对 Swift 代码：注意 mangled 符号（`$s` 开头），用 `swift-demangle` 还原；IDA 新版本与 Ghidra 均有 Swift demangle 支持

### 阶段 2 — 定位检测逻辑（见第三部分 checklist）

### 阶段 3 — 还原判定链
对每个命中的检测点：
1. 从 API 调用处出发，向上回溯谁调用了它（xref to）
2. 向下跟踪返回值如何汇入最终的布尔判定
3. 还原汇编 → 伪代码，记录函数地址、所属 image、判定逻辑
4. 标注这是"本地直接判定"还是"结果写入某字段后参与后续网络请求"
5. 对联动到业务风控的检测点，继续向上追到业务入口（福利、广告、商城等），还原"检测 → 业务降级"的完整调用链

### 阶段 4 — 辅助验证（非主线）
当某个 App 的某处逻辑因混淆、加壳或延迟触发而看不清时，到另一个 App 中查找对应实现来补全印证。判定两处是否为同一逻辑的参考依据：

| 参考维度 | 说明 |
|---|---|
| mangled 符号名 | 完全相同的 C++/Swift mangled 符号 → 强参考 |
| 字符串常量表 | 相同的越狱路径黑名单、顺序一致 → 强参考 |
| 函数结构 | 基本块数量/布局/调用顺序高度一致 → 中强参考 |
| framework 名 | 内嵌同名 framework → 强参考 |
| 常量/magic | 相同的加密 key、相同的指纹字段名 → 中强参考 |

此步骤仅用于补全证据、提高单点结论可信度，不单独产出"横向对比"结论。

### B. 导入符号 / 函数调用点搜索（IDA: Imports 窗口 / Ghidra: Symbol Tree→Imports）
定位下列符号的所有调用点（xref），逐个判断是否用于检测：

**文件系统**
```

```
**动态库 / dyld**
```

```
**反调试 / 系统调用**
```

```
**挂载 / 文件系统状态**
```

```
**URL Scheme**
```

```
**签名 / 进程信息**
```
csops  SecTaskCreate  task_info  proc_pidpath  _NSBundle_...
```

### C. Objective-C 方法命名扫描（class-dump 或 IDA 的 Classes 窗口）
搜方法名/类名中包含下列词根的项：
```
Jailbreak  jailbroken  detect  Detect  security  Security
check  Check  verify  risk  Risk  integrity  environment
device  Device  fingerprint  safe  Safe  tamper  hook
```
字节系常见自研前缀（经验性，需现场核实）：如 `BD`、`TT`、`AWE`（抖音 Aweme）、`Tomato/Novel`（番茄）等类前缀，可用于区分组件归属。

### D. Swift 符号还原
- 对 `$s` 开头的 mangled 符号跑 demangle，关注还原后含 `Jailbreak/Security/Risk/Detect` 的类型与方法
- Swift 的检测逻辑常封装在 struct/enum 的计算属性里，注意 getter 符号

### E. 内嵌 Framework 专项
- 逐个分析 `xxx.app/Frameworks/*.framework`，定位安全/风控相关组件
- 对已定位的安全 framework，优先还原其对外导出的检测入口函数
- （辅助）若某 framework 在多个 App 中同名出现，可对其做二进制 diff（BinDiff / Ghidra Version Tracking / Diaphora），借清晰的一方补全另一方被混淆的逻辑

## 附录：静态分析注意事项

- **大体积二进制**：抖音主二进制极大，IDA 初次分析耗时长，建议先只分析定位到的 framework 和关键函数区段
- **混淆**：字节系安全组件可能有字符串加密、控制流平坦化（OLLVM 风格）。若字符串搜不到明文，重点转向：常量解密函数的 xref、`+[... load]` 初始化时机、以及对导入符号调用点的直接排查。此时另一 App 中混淆较轻的同类实现可作为补全参考。
- **延迟触发**：部分检测不在启动时执行，而在进入特定业务（如商城、提现）时才触发，需从业务入口函数反向定位，而非只看 `application:didFinishLaunching`
- **服务端边界**：纯静态无法看到服务端下发逻辑，凡涉及"采集后上报再由服务端判定"的部分，只能还原到采集与上报点，服务端决策须明确标注为静态不可见
