## 目标 A —— fopen 五探针的调用者与触发时机：**已证实（静态腿结论被动态改写）**

### A-1 静态腿：`probe_fopen5` 是**死代码**

对 `0x10250F8C4` 做三种编码的全量引用搜索，**全部 0 命中**：

| 搜索 | 覆盖 | 命中 |
|---|---|---|
| `ADRP+ADD/LDR` 物化 | fanqie 全 `__text`（296 MB，4,960,391 条） | 0 |
| chained-fixup 指针槽 | 全文件 | 0 |
| 相对指针 `field_addr + int32/int64` | 全 `__TEXT`/`__DATA_CONST`/`__DATA` | 0 |

### A-2 动态腿：一次真实的会话里 `probe_fopen5` **调用 0 次**

`probeN = 0`（22 s 会话，含 `isEnvAbnormal` 被调用 20+ 次）。静态"零引用"与动态"零执行"互证 → **`0x10250F8C4` 在本版本上是死代码**。

### A-3 真正跑在链上的是 `statfs` 版，且调用链完整打出

backtrace（Frida 权威符号化）给出原报告缺的那条链：

```
+[SSLaunchMonitor markFirstClassLoad] / HMD 上报路径
 └─ +[HMDTTMonitorHelper reportHeaderParamsWithInjectedInfo:]      （性能上报）
 └─ -[HMDExceptionModuleReporter _reportExceptionData]             （异常上报）
 └─ +[HMDConfigHelper requestHeaderFromProvider:]                  （远程配置拉取）
      └─ -[HMDUploadHelper headerInfo]          0x10A09EDBC
           └─ -[HMDInfo isEnvAbnormal]          0x10A09F728
                └─ 0x10A09F744  →  0x10A09F764（dispatch_once 包裹）
                     └─ 0x10A09F79C  sandbox_statfs93_obw
```

- **触发时机**：不是"启动时一次"，而是**每次构造 HMD 上报 header 时**（三条并列路径：性能上报 / 异常上报 / 配置拉取），沙盒测试结果被 `_dispatch_once_callout` 缓存复用。
- 结论：**已证实**；对原报告影响 = **修正**（原报告 §3.1.2 把 `fopen` 五探针当作"真正跑在请求路径上的探针"，实际在跑的是 `statfs` 版；`fopen` 版本在本 build 未被调用）。

## 目标 B —— sysctl 反调试：**形态已证实，实测未命中**

### 动态证据（mib 真值）


- `[1,14,1,24794]` = `CTL_KERN / KERN_PROC / KERN_PROC_PID / getpid()` → **经典 P_TRACED 探针形态**（`24794` 即当次进程 pid）。
- 返回结构 648 B；按 arm64 `kinfo_proc` 布局，`p_flag` 位于 **0x20**（同结构内 `p_pid`@0x28 实测 = `0x60da` = 24794，与 pid 完全吻合，反证布局正确）。
- **`p_flag = 0x04004004`，`P_TRACED(0x800)` 未置位**。

### 交叉印证

- 一致：静态侧「`_ptrace` 未导入、只有 `sysctl`」与动态侧「只出现 KERN_PROC_PID」吻合。
- **新结论（动态独有）**：Frida 的注入方式**不设置 `P_TRACED`**，所以这条探针在 Frida attach 下读到的就是"未被调试"。
- 其余 `sysctl` 调用全是 `uname()` 内部（mib `[1,1]/[1,10]/[1,2]/[1,4]/[6,1]`）与 `sysctlbyname` 的设备指纹采集（`kern.osproductversion`、`hw.machine`、`kern.osversion`、`hw.memsize`、`hw.cpufamily/cputype/cpusubtype/ncpu`）、以及 `hw.ncpu`/`processorCount`。
- 结论：**已证实**（形态 + 偏移 + 实测值）。原报告 §3.4 的"推测 P_TRACED"升级为证实；同时否证"该探针能发现 Frida"。
- 未解释项：启动窗口内 attach 导致进程被杀，与 `P_TRACED` 无关（实测未置位），暂标 **待查**。

### A-5 「文件探测」其实有第三条实现：`NSFileManager fileExistsAtPath:`

`-[CJPayEnvManager hasJailBreakFiles]`（0x1074B7034，本次已按 +8 校准）反汇编是一个**数组遍历 + 逐项判定**：

```

0x1074b7038: bl    #0x109e0dfcc

0x1074b7050: ldr   x21, [x9, #0xbe0]     ; selref: objectAtIndexedSubscript:
0x1074b7058: ldr   x22, [x9, #0xec0]     ; selref: fileExistsAtPath:
0x1074b7060: mov   x24, x8               ; 索引/计数
0x1074b7068: bl    #0x1074b738c          ; cmp x0,x24
0x1074b706c: b.ls  #0x1074b70ac          ; 遍历结束
```

## S3 —— 重要修正：我此前对「roothide 字符串消费者」的判断是错的

**旧结论（第 2 轮）**：`0x112F15C00–0x112F16000` 有 7 处代码引用（0x10185AF08 等），构成"密文指针 + 校验函数"配对表。

| 检查 | 结果 |
|---|---|
| `adrp+add/ldr` 物化到 `0x112F15C00..0x112F16000`（全 __text，寄存器被覆盖即止） | **0** |
| 数据段中指向该区间的 chained 指针槽 | **0** |
| 相对指针（field+int32/int64） | **0**（此前已测） |

- 静态没有任何代码/指针引用它（三种编码 × 三个可执行节 × 数据段全 0）；

# 规则引擎与跨 App 比对（静态 + 定位）

## C1 —— 规则引擎的取值原语（已还原）

两个 helper 极短，语义明确：

```asm
; x0 = ctx, w1 = field index
0x1019a08e4: add x8, x0, w1, uxtw #3      ; x8 = ctx + idx*8
0x1019a08ec: ldr x0, [x8, #0x6070]        ; 读 ctx->fields[idx]
0x1019a08ec: ret

0x1019a08f0: add x8, x0, w1, uxtw #3
0x1019a08f8: str x2, [x8, #0x6070]        ; 写 ctx->fields[idx]
0x1019a08fc: ret
```

即：存在一个 **字段数组** `ctx + 0x6070 + idx*8`。`CF0…CFD` 这些"规则"本质上是**对字段数组做读/写/比较的小步骤**：

- `CF0 (0x10185A9B0)`：调 `0x107C1516C`（分支岛 → `0x10A542664`）取一个值，写进 **field[6]**
- `CF1 (0x10185A9DC)`：读 field[8]、field[9] 后比较
- `CF2 (0x10185AA14)`：同样读 field[8]、field[9]，再组合
- `CF3 (0x10185AA60)`：读 field[8]，调 `0x107C15178`（→ `0x10A006C7C`），用 field[6] 作参数

—— 这是**规则/表达式求值器**的步骤函数，不是"检查项"本身。`G0` / `F0` 更像控制流标记（goto / function）。

## C2 —— 这套东西属于 HMD 的 SafeGuard 子模块（关键连线）

跨 App 字符串检索发现一条路径：

```

```

而抖音的加密池里解出：`com.bytedance.safeguard.data`。

把它与前面的发现串起来：

这解释了 R3 的"明文从未出现"：**这些串是崩溃/上报路径（crash capture）按需解密的**，正常刷 App 不会走到。

三者签名完全一致。结论（已证实的"缺席"）：**该子系统的入口不由静态引用可达**，必然通过运行期计算/表驱动分发。这也解释了原报告为何会觉得"检测点零散、调用链断裂"——不是断，是静态不可达。

## C5 —— 下一步（动态，只读）

**探针思路**：既然规则引擎的读写原语是 `0x1019A08E4 / 0x1019A08F0`，就 hook 这两个**极小的字段读写函数**并计数。

- 若计数为 0 → 规则引擎在正常使用中不跑（可据此断定"roothide 规则未参与日常判定"）；
- 若计数 > 0 → 说明引擎在跑，进一步记录 `w1`（字段索引）分布，就能反推 `CF0…CFD` 到底碰哪些字段，从而还原规则语义。

这个探针**不需要触碰任何返回值**，且 hook 体里只有整数自增，安全。

## C6 —— 实测：规则引擎在正常会话中**完全没有运行**

按 C5 的探针思路，hook 字段读写原语 `0x1019A08E4`（读）/ `0x1019A08F0`（写），番茄 spawn → settle 4s → attach → 观测 17 s：

```

```

**17 秒内、一次都没调用。**

### 这条负结果的效力与边界

- **已证实**：attach 之后的正常使用窗口内，`CF0…CFD` 这套规则引擎**不参与任何判定**。
- **未覆盖**：启动最早期（t < 4 s）。因为 attach 必须等到 ≈3–4 s 才稳定（更早会把进程打死，已实测），所以"启动瞬间是否跑过一次"没有排除。

### 静态证据 1：mib 常量

```

0x106C873D8: stur d0, [x29, #-0x28]
```

### 雕刻法

按目标 ±1~4 KB 取窗口，包成最小 ELF64（`PT_LOAD.p_vaddr` = 原虚拟地址，`p_offset` = 0x1000），`open_database(run_auto_analysis=False)` → `add_func` → `decompile`。跨切片调用显示为 `MEMORY[addr]()`，地址与原始二进制一致。

产物：`analysis/fanqie/hexrays_f5.md`（1,242 行，11 个函数）。

### Hex-Rays 与手工逆向的交叉验证（全部一致）

| 目标 | 反编译结果 | 与我的结论 |
|---|---|---|
| `dec_v1` 0x109F8B83C | `HIDWORD(v6)=*(a2+v4)^0xDEADBEEF; *(a1+v4)=v6>>23;` 尾部 `*(byte)=*(byte)^(0xDEADBEEF>>v7)` | **完全一致**（整词 XOR+ROR23、尾部逐字节异或 key>>8j） |
| `sandbox_statfs93` 0x10A09F79C | `while(v0!=344)` → 43 项；`while(v0!=400)` → 50 项；`MEMORY[0x109E3C608](0x1136AD0D6, 514)`；`if ((fd & 0x80000000)!=0) v1=1; else { close; unlink; v1=0; }` | **完全一致**（43+50、`/hmd_tmp_file`、O_RDWR\|O_CREAT=0x202、fd 符号位判定） |
| `vm_get/vm_set` 0x1019A08E4/F0 | `return *(qword*)(a1 + 8*a2 + 24688);` | **24688 = 0x6070**，与手工一致 |
| `pred_inject_substr` 0x1083E1854 | `if (v2 == 40) goto LABEL_7;` 循环，逐项 `MEMORY[0x109EDFBC0](img, *(0x119055038 + v2))` | **40/8 = 5 项**，与"5 子串表"一致 |
| `isJailBreak` 0x1074B6FF4 | 两个调用结果 OR（`&1`），再尾调第三个 | 与"三探针聚合"一致 |
| `sysctl_caller` 0x106C873C4 | `*(v0-40)=MEMORY[0x112D0BA38]; *(v0-32)=1; *(v0-28)=pid;` 之后 `v5=0; if(!v4){...浮点...}` | **mib={1,14,1,pid} 且无 0x800 判定**，与 G1 一致 |

结论：手工逆出的算法与 IDA 反编译**逐条对得上**，没有出现需要推翻的差异。

**代价与局限**：雕刻法只能看单函数，跨切片的调用目标不可见；因此它适合**验证**已定位的函数，不适合替代全库分析。
